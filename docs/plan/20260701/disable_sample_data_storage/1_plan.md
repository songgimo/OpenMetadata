# Phase 1: Strategic Vision & Requirements (@planner)

## 🎯 목표 (Goal)
오픈메타데이터 서버 내부에 어떠한 형태의 **실제 데이터(Sample Data)도 저장되지 않도록** 원천적으로 차단하거나 정책을 강제합니다.

## 💡 배경 및 필요성 (Why)
오픈메타데이터는 기본적으로 테이블 구조 및 리니지 등의 메타데이터를 관리하는 플랫폼입니다. 하지만 데이터 프로파일러(Data Profiler) 동작 시 사용자의 편의를 위해 소량의 실제 데이터(Sample Data)를 가져와 내부 DB에 저장하는 기능이 켜져 있습니다. 
보안 요구사항(개인정보 보호, 망분리 규정, 데이터 외부 유출 방지 등)이 엄격한 환경에서는 메타데이터 플랫폼에 실제 데이터가 적재되는 것이 심각한 보안 결함이 될 수 있으므로, 이를 확실하게 방지해야 합니다.

## 🚀 기획 및 해결 방향 (What)
이 문제를 해결하기 위해 다음과 같은 3가지 접근 방식을 고려할 수 있습니다.

### 옵션 A: 인제스천(Ingestion) 파이프라인 설정 레벨에서의 차단 (가장 일반적)
- **내용**: 오픈메타데이터 UI 또는 Python Ingestion 프레임워크 설정에서 모든 DB 연결의 `generateSampleData` 옵션을 `false`로 강제합니다.
- **장점**: 코드 수정 없이 설정만으로 해결 가능합니다.
- **단점**: 사용자가 실수로 UI에서 옵션을 켜면 데이터가 저장될 위험이 여전히 존재합니다.

### 옵션 B: 백엔드(Java API) 레벨에서의 원천 차단 (Hard Block)
- **내용**: 오픈메타데이터 서버(Dropwizard) 코드 로직을 수정하여 `sampleData`를 저장하는 REST API 요청(`PUT/POST`)이 들어오면 에러를 반환하거나 데이터를 무시(Drop)하도록 변경합니다.
- **장점**: 사용자가 UI에서 샘플 데이터를 수집하도록 설정하더라도 서버 단에서 원천 차단되므로 가장 안전합니다.
- **단점**: 코어를 수정해야 하며 향후 오픈메타데이터 버전 업그레이드 시 유지보수 비용이 발생할 수 있습니다.

### 옵션 C: 샘플 데이터 저장소 외부 우회 (Storage Config)
- **내용**: `sampleDataStorageConfig`를 이용하여 샘플 데이터를 내부 DB(MySQL/PostgreSQL)가 아닌 폐쇄된 스토리지(예: 접근이 차단된 외부 버킷)로 향하게 하거나 더미 스토리지 인터페이스를 구현합니다.
- **장점**: 아키텍처 상의 기본 기능을 우회하는 공식 지원 방식에 가깝습니다.
- **단점**: 인프라 설정이 추가로 필요할 수 있습니다.

2. 이미 오픈메타데이터에 적재되어 있을지도 모르는 **기존 샘플 데이터의 일괄 삭제 쿼리(Migration/Script)**도 함께 준비해 드릴까요?

사용자님의 방향성 답변을 주시면, 작동을 멈추고 기다렸다가 Phase 2 (`@arch` 설계)로 넘어가겠습니다.
